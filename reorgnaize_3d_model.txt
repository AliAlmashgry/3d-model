HOW TO ORGANIZE visual-search-standalone/index.html IF ALL THE CODE WILL BE USED
================================================================================

This is based on a dependency map of all 351 top-level definitions in
index.html. For each one I worked out which screens use it, and that decides
where it goes. The design workflow I launched failed (every agent hit the
session limit), so this is my own design, not checked by a second agent.
I did check the three risky points against the code: the /__lab routes,
the module-level variables that get reassigned, and the router that's missing.

Line numbers below refer to visual-search-standalone/index.html as of 2026-10-01.


USE VITE INSTEAD OF ESBUILD
---------------------------

I recommended esbuild before because the live part was only about 4k lines and
keeping double-click (file://) mattered more. With 20k lines of storefront going
live (home, search, category listing, product page, cart, blog, 3D), Vite is the
better fit:
  - It reloads instantly while you edit.
  - It uses real npm React in production builds, instead of loading React from
    a CDN and compiling the JSX in the browser.
  - It can load each screen only when it's opened. The 3D screen and
    model-viewer are the heaviest part, and most visitors never open them.

The cost: double-clicking index.html stops working. You'd use `npm run dev`, or
open the built dist/ from a server.


THE RULES
---------

1. Code lives where it's used. If only one screen uses something, it goes in
   that screen's folder. If two or more screens use it, it goes down a level:
   data and plain logic to domain/, React components to shared/. Use by the
   demo screens doesn't count.

2. Imports only point downward: app -> features -> shared / domain.
   domain/ has no React and no imports from above it. Screens never import
   each other; to open another screen they call navigate("/p/"+key), which the
   code already does.

3. Each component imports its own CSS. Declare
   @layer base, shared, features, dev;
   once, so the order rules apply in doesn't depend on import order. Today some
   rules only win because they come later in the file (for example .loc-carbar
   overriding .car-bar).

4. Demos and the 3D tuning lab live in dev/. They're only reachable in
   development, and never from production code.

WATCH OUT
---------

- Module-level variables reassigned from other screens. Imports in ES modules
  are read-only, and these variables get reassigned from more than one place:
    - _searchCommitReset and _lastSearchQuery are set by the search overlay
      (12428) and by Discover (19400-19450).
    - PENDING_SEARCH_QUERY is set at 12407.
    - _enterCarAtTop is set at 11933.
  Moved into separate files as they are, each of those assignments would throw
  a TypeError. Wrap them in one object per concern (navState, searchSession) or
  give them setter functions.

- The router has to be rebuilt. The prototype's original routing App is gone;
  only useHashRoute, navigate and isModalRoute remain. Wiring every screen up
  means writing app/App.jsx and routes.js from scratch.

- lab-server. Change its INDEX path to public/car-registry.js; its regex and the
  one-car-per-line format stay the same. Every lab API call goes through
  /__lab/*, so the single Vite proxy rule covers it, draft previews included.
  The ?tune=1 lab becomes a dynamic import() that finishes before the first
  render. That avoids the load-order trap where the app reads window.car3dLab
  before the lab has run.

- Headless tests. .render/page.mjs should point at `vite preview`. The selectors
  (#vss-car, .vss-card, data-model-ready) don't change.


ORDER OF WORK
-------------

1. Commit. Commit your uncommitted work and tag it.
2. Set up Vite. Add the Vite scaffold and move the whole <script> into
   src/legacy.jsx and the whole <style> into legacy.css, unchanged. Get the page
   working on Vite.
3. Fix the mutable variables. Turn them into objects or setters. Fix any errors
   that Babel's const->var conversion was hiding.
4. Write tests first. Add tests that lock in today's output from the domain/
   data (catalog rows, partKind, findProduct, car names).
5. Move files out, starting from the bottom. Go domain -> shared -> each
   feature -> app, one commit per folder, moving code without changing it.
6. Move the CSS beside its components. Do it per feature, comparing screenshots
   of the main screens before and after each move.
7. Build the router App and the providers. Wire up each screen one at a time,
   starting with home, then discover, search, pdp, cart and blog.
8. Only then refactor. Remove the duplicate code in the two locate screens,
   split up CarStage3D and break up DiscoverScreen. Fix the known bugs at this
   point too.
